# POS → Payments contract

Status: Proposed for G0 review; not implemented or approved yet.

Author/Payments DRI: @cheshari-pearl. POS reviewer: @aine-mbabazi.

This proposal defines the boundary for recording a sale and collecting payment.
It uses Daraja sandbox only. Examples contain synthetic identifiers; never
commit real customer data, phone numbers, credentials, or payment payloads.
The Commission → Payments B2C contract will be specified separately.

## Ownership and trust

- POS owns tenants, sales, the sale total, and the sale's paid state.
- Payments owns payment attempts, provider interaction, callbacks, and reconciliation.
- POS calls Payments using authenticated service identity and verified tenant
  context. A tenant ID in a request body alone is not authorization.
- Each service accesses only its own database schema. POS reads payment status
  through the Payments API, never by querying the Payments schema.
- Payments checks tenant access on creation and status reads. A payment from
  another tenant returns `404` without exposing its details.

## Create a payment attempt

Proposed internal endpoint: `POST /payments`.

Required header: `Idempotency-Key`, generated by POS and retained for retries
of the same operation, including after a network timeout.

| Body field | Contract |
|------------|----------|
| `tenant_id` | Nonempty tenant identifier; must match authorized tenant context |
| `sale_id` | Identifier of a persisted, unpaid sale belonging to that tenant |
| `amount_minor` | Positive integer amount in minor units, taken from the persisted sale total |
| `currency` | `KES` for this capstone; 100 minor units represent KES 1 |
| `customer_phone` | Sandbox test number supplied at runtime, normalized to international format |

POS validates the sale and submits its authoritative amount. Payments validates
the request and persists an attempt before contacting Daraja. Amount and currency
are immutable for that attempt. The provider adapter must validate representable
amounts before dispatch; it must never silently round money.

A newly accepted request returns `202 Accepted` with a durable payment ID:

```json
{
  "payment_id": "payment_demo_001",
  "tenant_id": "tenant_demo_001",
  "sale_id": "sale_demo_001",
  "amount_minor": 10000,
  "currency": "KES",
  "status": "pending"
}
```

Acceptance means Payments has recorded the request, not that the customer has
paid. POS retains `payment_id` to check the result.

| Response | Meaning |
|----------|---------|
| `400` | Invalid or missing fields; no provider request is sent |
| `401` / `403` | Missing identity or insufficient permission |
| `409` | Idempotency key reused with different input, or another attempt is pending/succeeded for the sale |
| `503` | Request could not be durably accepted; retry using the same key |

## Status and POS confirmation

Proposed internal endpoint: `GET /payments/{payment_id}`. An authorized read
returns `200` with the same fields as the creation response and the latest status.
An unknown or inaccessible payment returns `404`.

For the initial implementation, POS polls this endpoint with bounded backoff
while the payment is pending. POS also needs a background retry path so closing
the browser or a POS restart cannot prevent eventual sale confirmation. Polling
intervals and reconciliation timing must be agreed before G2.

POS marks a sale paid only after Payments reports `succeeded`, checking the
tenant, sale, amount, and currency against its own record. Applying that result
must be idempotent. Browser responses and raw provider callbacks cannot mark a
sale paid. Commission eligibility begins only after POS records it as paid.

## Payment state transitions

| Current state | Evidence / event | Result |
|---------------|------------------|--------|
| No attempt | Valid request durably accepted | `pending` |
| `pending` | Verified provider success matching this attempt | `succeeded` |
| `pending` | Verified definitive decline/cancellation/failure | `failed` |
| `pending` | Timeout, unavailable dependency, missing or unverified callback | Remain `pending`; reconcile |
| `succeeded` / `failed` | Duplicate matching result | No state change |
| `succeeded` / `failed` | Conflicting result | Preserve state; flag for investigation |

`failed` requires a definitive outcome, not merely an HTTP error or elapsed time.
Terminal states are not automatically reversed. Refunds are outside this proposal.

Callbacks are untrusted input. Correlate them to a persisted attempt and verify
the outcome through provider-supported mechanisms before changing payment state,
consistent with the threat model. The exact sandbox verification/query mechanism
must be validated during integration; this proposal assumes no specific callback
signature support.

## Duplicate handling and uncertain outcomes

- Enforce database uniqueness on `(tenant_id, idempotency_key)`. Concurrent
  requests using the same key resolve to the same durable attempt.
- Store a canonical request fingerprint. The same key and same input return
  the existing payment ID and current status (`202` pending, `200` terminal),
  without sending another STK request. Different input returns `409`.
- Enforce at most one pending or succeeded attempt per tenant/sale, including
  concurrent requests with different keys. After a definitive failure, an
  explicit new customer attempt may use a new key; the failed attempt remains
  in the audit history.
- Persist provider correlation identifiers and processing outcomes. Apply a
  callback's state transition atomically; replay must have no additional effect.
- A database idempotency key does not make an external API call exactly once.
  If dispatch times out or a worker crashes after sending, keep the attempt
  pending and reconcile. Do not blindly resend or permit a replacement attempt
  while the provider outcome is unknown. Unresolvable attempts require operator
  investigation with an audit trail.
- Redact customer phones and credentials from logs. Retain only the sensitive
  data required for processing, protected by access controls.

## Acceptance scenarios for G2

1. A successful sandbox payment marks the correct tenant's sale paid once.
2. Sequential and concurrent retries with the same key produce one attempt.
3. Reusing a key with changed amount, sale, or phone returns `409`.
4. A different key cannot initiate another payment for a pending or paid sale.
5. Duplicate or delayed callbacks cannot apply payment success twice.
6. A timeout or crash after dispatch stays pending; reconciliation resolves
   it without blindly initiating another charge.
7. A definitive decline leaves the sale unpaid and allows an explicit new attempt.
8. Cross-tenant reads and writes are rejected without leaking payment data.
9. A POS restart after payment success eventually records the sale paid once.
10. Invalid or conflicting callbacks cannot mark a sale paid and are surfaced
    for investigation.

## Review decisions before implementation

- Agree on endpoint names, payload fields, service authentication, and how
  verified tenant context reaches Payments.
- Confirm sale totals cannot change while a payment is pending, and define
  how POS enforces this restriction.
- Validate sandbox amount/phone requirements and outcome verification support.
- Agree on polling/reconciliation timing and escalation for unresolved attempts.
- Specify commission rules and the B2C payout contract in a follow-up proposal.
