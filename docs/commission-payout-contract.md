# Commission → Payments payout contract

Status: Proposed for G0 review; not implemented or approved yet.

Author/Payments and Reliability DRI: @cheshari-pearl. Reviewers: the Commission
and Platform owners.

This proposal defines the internal boundary used when the Commission service
requests an M-Pesa B2C payout. It uses Daraja sandbox only. Examples contain
synthetic identifiers. Never commit real customer data, phone numbers,
credentials, or payment payloads.

## Ownership and trust

- Commission owns eligibility, commission calculation, the daily close run, and
  its payout ledger.
- Payments owns payout attempts, Daraja B2C interaction, callbacks, transaction
  queries, and reconciliation.
- Commission must never call Daraja directly. All B2C requests go through the
  authenticated Payments API.
- Commission calls Payments with an authenticated service identity and verified
  tenant context. A tenant ID supplied in the request body alone is not
  authorization.
- Each service accesses only its own database schema. Commission gets a payout
  result through the Payments API, never by reading the Payments schema.

## Request a payout

Proposed internal endpoint: `POST /payouts`.

Required header: `Idempotency-Key`, generated by Commission and stored with its
payout-ledger entry. Commission must reuse the key whenever it retries the same
payout after a timeout, restart, or scheduled-job rerun.

| Body field | Contract |
|------------|----------|
| `tenant_id` | Nonempty tenant identifier; must match authorized tenant context |
| `attendant_id` | Identifier of the eligible attendant for this payout |
| `commission_run_id` | Identifier of the daily close run that calculated the payout |
| `amount_minor` | Positive integer amount in minor units, calculated from confirmed paid sales only |
| `currency` | `KES` for this capstone; 100 minor units represent KES 1 |
| `recipient_phone` | Sandbox test number supplied at runtime, normalized to international format |

Commission calculates and persists the eligible amount before calling Payments.
Payments validates the request and records a durable payout attempt before any
provider interaction. Amount and currency are immutable for that attempt. The
provider adapter validates representable amounts before dispatch and must never
silently round money.

A newly accepted request returns `202 Accepted`:

```json
{
  "payout_id": "payout_demo_001",
  "tenant_id": "tenant_demo_001",
  "attendant_id": "attendant_demo_001",
  "commission_run_id": "commission_run_demo_001",
  "amount_minor": 2500,
  "currency": "KES",
  "status": "pending"
}
```

Acceptance means Payments durably recorded the payout request. It does not mean
the attendant received money. Commission retains `payout_id` and keeps its own
ledger entry pending until Payments confirms success.

| Response | Meaning |
|----------|---------|
| `400` | Invalid or missing fields; no provider request is sent |
| `401` / `403` | Missing identity or insufficient permission |
| `409` | Key reused with different input, or a pending/succeeded payout already exists for the same ledger item |
| `503` | Request could not be durably accepted; retry with the same key |

## Read payout status

Proposed internal endpoint: `GET /payouts/{payout_id}`. An authorized read
returns `200` with the same fields as the creation response and its latest
status. An unknown or inaccessible payout returns `404`.

Commission polls pending payouts with bounded backoff and also has a background
retry/recovery path so an interrupted daily close can resume safely. It marks a
ledger item paid only after Payments returns `succeeded`, checking tenant,
attendant, commission run, amount, and currency against its own record.
Applying the result must be idempotent.

## Payout state transitions

| Current state | Evidence / event | Result |
|---------------|------------------|--------|
| No attempt | Valid request durably accepted | `pending` |
| `pending` | Verified provider success matching this attempt | `succeeded` |
| `pending` | Verified definitive failure or rejection | `failed` |
| `pending` | Timeout, unavailable dependency, missing or unverified callback | Remain `pending`; reconcile |
| `succeeded` / `failed` | Duplicate matching result | No state change |
| `succeeded` / `failed` | Conflicting result | Preserve state; flag for investigation |

`failed` requires a definitive provider outcome. An HTTP error, job timeout, or
missing callback must not mark a payout failed. Terminal results are not
automatically reversed. Reversals and refunds are outside this proposal.

Provider callbacks are untrusted input. Payments correlates them with a stored
payout attempt and verifies the outcome through Daraja-supported mechanisms
before changing state. The exact sandbox query and callback-verification flow
will be validated during integration.

## Duplicate handling and uncertain outcomes

- Payments enforces database uniqueness on `(tenant_id, idempotency_key)` and
  stores a canonical request fingerprint. The same key with the same input
  returns the existing attempt; changed input returns `409`.
- Payments enforces at most one pending or succeeded payout per Commission
  ledger item. The ledger item must be identified by `tenant_id`,
  `commission_run_id`, and `attendant_id`; Platform and Commission must agree
  on the final database identifier before implementation.
- Commission uses the same ledger item and idempotency key on a job rerun. It
  must not create a new payout request merely because its process restarted.
- Provider correlation IDs and processing outcomes are persisted. Callback
  state transitions are atomic, so replay has no additional effect.
- A database key cannot make an external B2C call exactly once. If a worker
  crashes after dispatch or the provider call times out, leave the attempt
  pending and reconcile. Do not blindly resend or issue a replacement while the
  provider outcome is unknown.
- Redact recipient phones and credentials from logs. Retain only sensitive data
  required for processing and protect it with service access controls.

## Acceptance scenarios for G2

1. A successful sandbox B2C payout marks exactly one Commission ledger item
   paid for the correct tenant and attendant.
2. Sequential and concurrent retries with the same key return one payout
   attempt.
3. Reusing a key with a changed amount, attendant, run, or recipient returns
   `409`.
4. Re-running a daily close cannot create a second pending or successful payout
   for the same ledger item.
5. A duplicate or delayed callback cannot mark the payout successful twice.
6. A timeout or crash after dispatch remains pending; reconciliation resolves
   it without blindly sending another B2C request.
7. A definitive failure leaves the ledger unpaid and preserves an audit trail
   for the team to decide whether a later retry is eligible.
8. Cross-tenant payout reads and writes are rejected without leaking data.
9. A Commission restart after payout success eventually records the ledger item
   paid exactly once.
10. Invalid or conflicting callbacks cannot mark a payout successful and are
    surfaced for investigation.

## Decisions needed before implementation

- Agree on endpoint names, payload fields, service authentication, and how
  verified tenant context reaches Payments.
- Define the Commission ledger item's final identifier and whether one daily
  run can intentionally create more than one payout per attendant.
- Confirm the eligible-sales cutoff, commission-rate source, and daily close
  schedule for each tenant.
- Validate Daraja sandbox B2C recipient, amount, callback, and transaction-query
  requirements.
- Agree on polling/reconciliation timing, failed-payout retry policy, and
  escalation for payouts still pending after the daily completion target.
